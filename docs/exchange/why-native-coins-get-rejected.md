# Why Native Coins Get Rejected by Exchanges

**Category:** Documentation
**Status:** Draft
**Last reviewed:** 2026-07-02

## Summary

This page tracks common reasons a native blockchain coin may be rejected, delayed, or deprioritized by an exchange.

It is written as a prevention checklist. The goal is to fix avoidable problems before an application is submitted.

## 1. The exchange cannot quickly understand the project

Common symptoms:

- No clear project summary.
- Website is incomplete or outdated.
- Ticker, chain name, and branding are inconsistent.
- Documentation uses hype instead of technical facts.
- Claims are not linked to sources.

How to reduce risk:

- Maintain one canonical project summary.
- Keep the official website, repository, explorer, and release links current.
- Use plain technical descriptions.
- Avoid exaggerated claims.

## 2. The exchange cannot confirm the coin is alive

Common symptoms:

- Explorer is offline.
- Blocks are stale.
- GitHub activity appears abandoned.
- Latest release is old or unclear.
- Community links are dead.

How to reduce risk:

- Confirm current block production before submitting.
- Confirm the explorer is live.
- Confirm current release status.
- Record active community links with the date checked.

## 3. The exchange cannot safely integrate the software

Common symptoms:

- No clear daemon/node setup notes.
- No release checksums.
- No signed release artifacts.
- No build instructions.
- No upgrade guidance.
- No maintainer contact for urgent software questions.

How to reduce risk:

- Provide source repository and release links.
- Provide checksum/signature status honestly.
- Provide tested or clearly labeled setup notes.
- Provide an update-notification process.
- Provide a technical contact path.

## 4. The exchange cannot evaluate deposit risk

Common symptoms:

- No confirmation guidance.
- No reorg explanation.
- No network-health notes.
- No explorer history.
- No guidance for support investigations.

How to reduce risk:

- Document confirmation policy or a draft risk model.
- Link to reorg and confirmation explainers.
- Provide block explorer and network status references.
- Avoid pretending that a draft policy is final.

## 5. The exchange sees unresolved security or trust concerns

Common symptoms:

- Unsigned releases with no explanation.
- No security contact.
- No known-issues page.
- Unsupported audit claims.
- Claims about advanced protection without source-backed documentation.

How to reduce risk:

- Keep release-verification status visible.
- State honestly when audits are not found.
- Maintain a known-unknowns page.
- Do not promote unverified security claims.

## 6. The exchange sees weak market or community support

Common symptoms:

- No official social links.
- No community size snapshot.
- No visible user activity.
- No existing markets or liquidity plan.
- No launch/promotion plan.

How to reduce risk:

- Provide current social/community links.
- Provide dated community snapshots.
- Provide a realistic liquidity and market-support plan if requested.
- Avoid inflated follower or volume claims.

## 7. The project looks too risky legally or operationally

Common symptoms:

- Unclear team/contact process.
- ICO/presale language.
- Unclear supply distribution.
- Claims that could be interpreted as investment promises.
- No response path for compliance questions.

How to reduce risk:

- Use neutral project language.
- Avoid investment-return wording.
- Provide supply and emission documentation.
- Provide a contact path for exchange review.

## 8. The application is sent before the packet is ready

Common symptoms:

- Placeholder fields remain.
- Broken links are included.
- Old release information is submitted.
- Explorer was not checked the same day.
- Questions from the exchange require frantic follow-up.

How to reduce risk:

- Use [Exchange Readiness Checklist](exchange-readiness-checklist.md).
- Use [Exchange Listing Packet Template](listing-packet-template.md).
- Save the exact submitted packet and submission date.
- Track every exchange response and requested change.

## BC2-specific caution

BC2 should avoid overstating readiness until these are checked:

- Current release artifact verification.
- Current explorer status.
- Current official contact process.
- Current community links.
- Tested node/operator instructions.
- Confirmation policy.
