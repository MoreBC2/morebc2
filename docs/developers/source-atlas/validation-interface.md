# Validation interface

**Category:** Documentation
**Status:** Draft
**Last reviewed:** 2026-06-30

## Summary

This page covers a first-pass review of:

- `src/validationinterface.h`
- `src/validationinterface.cpp`

These files define the event interface used by validation and mempool code to notify interested subsystems about chain, block, and mempool events.

This is not consensus validation itself. It is the notification layer around validation events.

## Why this file matters

Many subsystems need to react when validation state changes.

Examples include:

- Wallets learning about new blocks or blocks leaving the active chain.
- Indexes updating after blocks connect.
- Services observing mempool additions and removals.
- Components waiting for validation event work to finish before continuing.

The validation interface helps keep these consumers decoupled from the validation code that generates the events.

## Subscriber model

`CValidationInterface` is the base class for subscribers.

Subscribers override event methods for items they care about.

The reviewed header says that each subscriber receives events in the order generated by validation and mempool. For a given subscriber, event work effectively runs with single-threaded memory consistency, meaning one event finishes before the next begins.

The same comment warns that no ordering should be assumed across different subscribers.

## Event types

Reviewed event methods include:

- `UpdatedBlockTip`
- `ActiveTipChange`
- `TransactionAddedToMempool`
- `TransactionRemovedFromMempool`
- `MempoolTransactionsRemovedForBlock`
- `BlockConnected`
- `BlockDisconnected`
- `ChainStateFlushed`
- `BlockChecked`
- `NewPoWValidBlock`

## Block tip events

`UpdatedBlockTip` notifies listeners when the chain tip advances.

The header notes that when multiple blocks are connected at once, this event may be called only on the final tip, not necessarily on every intermediate tip. Consumers that need every connected block should use `BlockConnected`.

`ActiveTipChange` notifies listeners any time the active tip changes synchronously.

## Mempool events

Reviewed mempool events include:

- Transaction added to mempool.
- Transaction removed from mempool.
- Transactions removed from mempool because a block was connected.

The header documents removal reasons for `TransactionRemovedFromMempool`, including expiry, size limit, reorg, conflict, and replacement.

It also explicitly says that normal inclusion in a block is handled through `MempoolTransactionsRemovedForBlock`, not `TransactionRemovedFromMempool`.

## Block connection and disconnection events

`BlockConnected` notifies listeners when a block connects.

`BlockDisconnected` notifies listeners when a block leaves the active chain.

The header notes that `BlockDisconnected` is only called for the active chainstate, because background chainstates should not disconnect blocks.

## Disk flush event

`ChainStateFlushed` notifies listeners that the active chain state is persisted on disk.

The header says that when this event is invoked, validation changes from prior events are guaranteed to exist on disk and survive restart, including unclean shutdown.

This matters for clients that maintain their own database state.

## Block checked and new work-valid block events

`BlockChecked` notifies listeners about a block validation result.

The header says that if the validation state is valid, the provided block is guaranteed to be the current best block at the time the event was generated, though not necessarily at event delivery time.

`NewPoWValidBlock` notifies listeners that a block building directly on the current tip has been received and connected to the headers tree, though not fully validated yet.

## Implementation model

`ValidationSignalsImpl` stores registered event subscribers using:

- An unordered map from subscriber pointer to list entry.
- A list of shared subscriber entries with reference counts.
- A task runner for queued background work.

The list/reference-count model lets unregistered subscribers stay alive until currently executing event work is finished.

## Queue behavior

Many events are queued through the task runner.

Reviewed events that are enqueued include:

- `UpdatedBlockTip`
- `TransactionAddedToMempool`
- `TransactionRemovedFromMempool`
- `MempoolTransactionsRemovedForBlock`
- `BlockConnected`
- `BlockDisconnected`
- `ChainStateFlushed`

Reviewed events that call subscribers directly in the current path include:

- `ActiveTipChange`
- `BlockChecked`
- `NewPoWValidBlock`

This distinction matters for ordering and thread assumptions.

## Queue synchronization

`FlushBackgroundCallbacks` flushes queued event work.

`CallbacksPending` reports the task runner queue size.

`CallFunctionInValidationInterfaceQueue` pushes a function onto the event queue after previously generated events.

`SyncWithValidationInterfaceQueue` waits for the queue to drain by inserting a promise-setting function and waiting for it.

The header warns that callers must be careful blocking while locks are held, especially around `cs_main`, because validation interface clients may need those locks and deadlock can result.
